## Как это устроено

| Что | Сейчас | После переключения |
|---|---|---|
| Страницы, скрипты, музыка, картинки | Vercel (сеть узлов по миру) | ONREZA, слой STATIC |
| Сервер `api/*.js` | функции Vercel, `arn1` — Стокгольм | ONREZA Compute (`server/index.js`), Ленинградская обл. |
| База аккаунтов, прогресса, жалоб и всего остального | **PostgreSQL ONREZA**, таблица `inflatia_kv` — переменная `DATABASE_URL` | та же |
| Исследование | **та же база**, таблица `inflatia_research` (своя цель и свои права доступа — `research/data-dictionary.md`, раздел 1) | та же |
| Старая база | Upstash Redis, `iad1` (США) — копия на 20.11, не используется рабочим сайтом | та же, пока не удалена |

ONREZA пишет, что её инфраструктура — дата-центры Selectel в Санкт-Петербурге, Ленинградской области и Москве
(docs.onreza.ru → «Размещение данных и сведения для РКН»); основное хранилище PostgreSQL и резервные копии — Санкт-Петербург.

### Что сделано в коде

- `api/_lib/pgkv.js` — те команды Redis, которыми пользуется сервер (значения со сроком, счётчики, хэши, множества,
  списки), поверх таблицы PostgreSQL. Таблицы `inflatia_kv` и `inflatia_research` создаются сами при первом обращении;
  обе ходят через один пул соединений (не больше 3 на функцию).
- `api/_lib/store.js`: если задан `DATABASE_URL` — работает с PostgreSQL ONREZA и к Upstash не обращается. Не задан —
  как раньше, Upstash (так работают превью-сборки).
- `api/_lib/research-store.js`: исследование — в таблице `inflatia_research` той же базы `DATABASE_URL`. Без
  `DATABASE_URL` исследование закрыто (на Upstash оно не открывается).
- `api/_lib/research-link.js` — единственный мост между аккаунтами и исследованием: исследованию — только логин и год
  рождения; аккаунту — удаление участия вместе с аккаунтом и свои записи в «Скачать мои данные».
- `scripts/upstash-to-onreza.mjs` — перенос всех ключей из Upstash со сроками жизни.
- `scripts/db-backup.mjs` — резервная копия обеих таблиц, её проверка, развёртывание в другой базе и сравнение с копией
  Upstash.
- `/api/health` — какая база подключена и отвечает ли (без данных и адресов).
- Проверка — `api/__tests__/pgkv.test.js` на настоящем PostgreSQL: каждая команда отвечает так же, как Upstash; одновременные
  `incr` не теряются; блокировка `set nx` срабатывает один раз; две таблицы не смешиваются; исследование с одновременной
  записью одного аккаунта; копия снимается, разворачивается и сверяется.

## Перенос сервера в ONREZA Compute — подготовлено 24.11.2026, рабочий сайт пока на Vercel

Задача владельца 24.11.2026: обработка запросов и работа с персональными данными — на инфраструктуре ONREZA в России.
Код для этого готов и проверен (ниже, «Проверки»), но **рабочий сайт не переключался**: сайт и API по-прежнему отдаёт Vercel
(`inflatia.vercel.app`), Vercel не отключён, DNS и переменные Vercel не менялись. Переключение — после проверки тестовой
версии и решения владельца (раздел «Переключение»). Документация ONREZA, по которой это сделано, — docs.onreza.ru
(Compute, Build Output Manifest, Edge Rules, Фреймворки, Переменные окружения, Логи, PostgreSQL, «Размещение данных и
сведения для РКН»), прочитана 24.11.2026.

### Итоговая схема

Браузер → домен в ONREZA → Edge ONREZA (правила `onreza.rules.toml`: заголовки безопасности, адреса экранов) →
- всё, кроме `/api/*`, → слой **STATIC** «site» (собранный сайт `dist/`, CDN ONREZA);
- `/api/*` → слой **COMPUTE** «api» — Express-сервер `server/index.js` (Node.js 22/24) → **PostgreSQL ONREZA**, тот же
  `DATABASE_URL`, те же таблицы `inflatia_kv` и `inflatia_research`. Повторно переносить данные не нужно.

Один домен, запросы к API — с той же страницы (same-origin): CSP `connect-src 'self'` и вход по ключу остаются как есть.
ONREZA Functions не используются: им нужен полный Node.js с npm-зависимостями и общими модулями проекта.

| Что | Где по сведениям ONREZA (docs.onreza.ru → «Размещение данных и сведения для РКН», редакция 13.10.2026) |
|---|---|
| Сервер API (Compute) | «сборка и выполнение приложений» — Ленинградская обл., Всеволожский р-н, г.п. Дубровка, ЦОД Selectel |
| База: вычисления | там же, Дубровка |
| База: хранилище, журналы транзакций, резервные копии | Санкт-Петербург, ул. Цветочная, д. 19, стр. 1 (Selectel) |
| Файлы развёртываний | Санкт-Петербург, ул. Цветочная, д. 19 |
| DNS | Дубровка и Москва |
| Раздача статики (CDN) | **на странице не указано** — уточнить у поддержки ONREZA |
| Журналы запросов (Access Logs) | **место и срок хранения не указаны**; в журнале — время, метод, путь, код ответа, длительность и **IP-адрес клиента**; на Hobby их видно 30 минут, на Pro — до 7 дней |

Это сведения провайдера, а не вывод о соответствии 152-ФЗ: оформление обработки (оператор, поручение, уведомление РКН) —
`docs/legal-todo.md`. На Hobby ONREZA подписываемых поручений обработки не даёт.

### Что в репозитории

| Файл | Что делает |
|---|---|
| `server/index.js` | точка запуска: слушает `PORT` на `0.0.0.0`; без `DATABASE_URL` не стартует; SIGTERM — закрывает HTTP-сервер и пул базы, выход 0 |
| `server/app.js` | Express: все `/api/*` → те же обработчики `api/*.js`; тело JSON до 4,5 МБ; адрес клиента от доверенного прокси; заголовки безопасности и `no-store` у API; без CORS |
| `server/routes.js` | список маршрутов (девять `api/*.js`) и адреса экранов приложения |
| `server/headers.js` | заголовки безопасности — те же, что в `vercel.json` |
| `api/_lib/client-ip.js` | адрес клиента для ограничений частоты — один для всех обработчиков |
| `scripts/build-onreza.mjs` | `npm run build:onreza`: сайт → `onreza-build/site`, сервер одним файлом → `onreza-build/api/index.mjs` (все зависимости внутри, `node_modules` не нужны), манифест → `onreza-build/.onreza/manifest.json`; сборка падает, если в сайт попал ключ ответов исследования |
| `onreza.rules.toml` | правила Edge: заголовки безопасности, `/book`, `/shop`… и `/book/<глава>` → `/index.html`, `Cache-Control` для `/assets/`, `/api/` — мимо кэша |
| `docs/api.md` | все маршруты, методы, действия и ограничения |

Код работает и на Vercel: обработчики не переписаны, `vercel.json` не тронут — откат на Vercel возможен в любой момент.

Маршруты манифеста: `/api` и `/api/*` → сервер (приоритет 20); адреса экранов (`/book`, `/league`, `/shop`, `/profile`,
`/world`, `/news`, `/research`, `/book/<глава>`) → сервер, он отдаёт копию `index.html` (10) — запасной путь, если правило
Edge не применилось; всё остальное → статика (0). Незнакомый адрес — 404, как на Vercel.

### Переменные окружения

Задаются в ONREZA: **Project → Settings → Environment Variables**, у секрета — признак Secret. Значения в чат и в код не
вставлять; в журнал сервер их не пишет.

| Переменная | Окружение ONREZA | Секрет | Что это | Откуда |
|---|---|---|---|---|
| `DATABASE_URL` | Production | да | строка подключения к той же базе | панель базы ONREZA → Подключение. **Сначала смените пароль** (ниже), потом новую строку — и в Vercel, и в ONREZA |
| `OWNER_LOGINS` | Production (и Preview, если превью проверяют владельцы) | да | логины владельцев через запятую: разбор жалоб, отчёты, ники | то же значение, что в Vercel (там оно Sensitive — значение помнит владелец) |
| `SITE_URL` | Production | нет | адрес сайта для `canonical` и `og:url` (сборка), например `https://<проект>.onreza.app` | новый адрес |
| `TRUST_PROXY_HOPS` | при необходимости | нет | сколько доверенных прокси перед сервером (по умолчанию 1) | проверка «Адрес клиента» |
| `CLIENT_IP_HEADER` | при необходимости | нет | имя заголовка с адресом, если ONREZA ставит такой и перезаписывает присланный | там же |
| `PG_POOL_MAX` | при необходимости | нет | соединений с базой на процесс, 1…10 (по умолчанию 3) | — |
| `PG_IDLE_MS` | при необходимости | нет | через сколько закрывать простаивающее соединение (по умолчанию 30 000) | — |

Не задавать в ONREZA: `KV_REST_API_URL`, `KV_REST_API_TOKEN`, `KV_REST_API_READ_ONLY_TOKEN`, `KV_URL`, `REDIS_URL` (Upstash в США;
сервер в Compute его не подключает, даже если задать), `MIGRATE_TOKEN` (адреса переноса больше нет), `ALLOW_MEMORY_STORE`
(только для локального запуска без базы), `DATABASE_CA` (сертификат базы подписан публичным центром; корень Минцифры
в Compute и так в доверенных, а явный CA отключает доверие платформы). Исследование закрыто — `RESEARCH_STATUS`,
`RESEARCH_ALLOC_SEED`, `RESEARCH_EXPORT_TOKEN` не задавать. Системные `PORT`, `NODE_ENV`, `ONREZA_ENV` ставит платформа.

**Preview.** Production-строку базы в Preview **не давать**. Для превью — ветка базы ONREZA (PostgreSQL → Ветки → создать,
её строка — в `DATABASE_URL` окружения Preview) или превью без базы: `ALLOW_MEMORY_STORE=1` только в Preview (данные живут,
пока жив процесс). Без одного из двух сервер превью не запустится — так и задумано.

### Что сделать в панели ONREZA (владелец)

1. **Сменить пароль базы** (раздел «Что сделать владельцу сейчас», п. 1) — до того, как строку получит второй сервис.
2. **Новый проект**: app.onreza.ru → Projects → Create → импорт из GitHub `PrimeLong/inflatia`. Production-ветка — `main`.
3. **Сборка** (Project → Settings → Сборка и развертывание): Build Command `npm run build:onreza`, Output Directory
   `onreza-build`, Install Command `npm ci`, Node.js 22 (на ней всё проверено; 24 тоже поддерживается).
4. **Переменные** — таблица выше.
5. **Правила Edge**: файл `onreza.rules.toml` лежит в корне репозитория. Если после первой сборки заголовки не появились
   (проверка ниже, п. 3), опубликуйте его содержимое вручную: Project → Edge Rules (или `nrz rules publish`).
6. **Автосон базы** (PostgreSQL → Настройки): по умолчанию база засыпает после простоя, и первый запрос после паузы её будит —
   это секунды на вход у первого ученика. Если медленный первый вход мешает — 1 час или 1 день (дороже по CU-часам).

### Проверки тестовой версии (до переключения)

Всё — на адресе, который ONREZA выдала проекту (`…onreza.app`). Учебные данные — только синтетические: отдельный тестовый
аккаунт, который в конце удаляется кнопкой «Удалить аккаунт». Лучше — превью на ветке базы (выше): тогда тест не касается
рабочей таблицы вовсе.

1. `https://<тест>/api/health` → `{"ok":true,"db":"postgres","research":"postgres","runtime":"onreza-compute",…}`.
2. **Адрес клиента** (от этого зависят лимиты входа и регистрации): `https://<тест>/api/health?proxy=1`. В ответе — только
   форма заголовков, без адресов. Нужно `"chosenPrivate": false`. Если `true` — сервер видит адрес прокси, и все ученики
   попадут в один счётчик: поставьте `TRUST_PROXY_HOPS=2` (если `xffEntries` ≥ 2 и `xffRightPrivate: true`) или
   `CLIENT_IP_HEADER` с именем заголовка из `otherIpHeaders`, пересоберите и проверьте снова. Документация ONREZA заголовок
   адреса клиента не описывает — это проверка на месте.
3. Заголовки и адреса:
   ```bash
   curl -sI https://<тест>/ | grep -i -E 'content-security-policy|x-frame-options|x-content-type'
   ```
   ```bash
   curl -s -o /dev/null -w '%{http_code} %{content_type}\n' https://<тест>/shop
   ```
   ```bash
   curl -s -o /dev/null -w '%{http_code}\n' https://<тест>/nope/deeper
   ```
   ```bash
   curl -s -o /dev/null -w '%{http_code}\n' -H 'Range: bytes=0-99' https://<тест>/music/anchor.mp3
   ```
   Ожидается: три заголовка на месте; `/shop` — `200 text/html`; `/nope/deeper` — `404`; `/api/nope` — `404` с JSON;
   музыка — `206` (CDN отвечает кусками: музыка играет потоком и после паузы продолжает с той же секунды; при `200`
   перемотка в Chromium не работает — спросить у поддержки ONREZA).
4. Ручная проверка (телефон и ПК, ~10 минут): регистрация тестового аккаунта → выход → вход → «Забыли пароль?» с кодом →
   урок и перезагрузка (прогресс на месте) → лавка и особые уроки → музыка (играет сразу, без долгой загрузки) → друг
   (второй тестовый аккаунт) → сетевая комната и чат → «Сообщить об ошибке» → «Скачать мои данные» → «Удалить аккаунт»
   у обоих тестовых аккаунтов. В конце — Project → Logs: нет `server error`.
5. `/api/research?action=status` → `not-started` (исследование закрыто).

**Двойная запись не грозит.** Пока работают оба (Vercel и ONREZA), они пишут в одну и ту же базу: состояния в памяти у
серверов нет (сессии, счётчики, комнаты — в PostgreSQL), атомарные операции — одной командой SQL, схема не меняется.
Ученик, вошедший на Vercel, остаётся тем же учеником на ONREZA. Соединений с базой: до 3 на каждый экземпляр функции Vercel
и до `PG_POOL_MAX` на процесс Compute.

### Переключение

**Своего домена у сайта нет** — только `inflatia.vercel.app` (проверено в Vercel 24.11.2026). Перенести поддомен Vercel в
ONREZA нельзя: после переключения у сайта будет **новый адрес** — `…onreza.app` или свой домен (Project → Settings →

2. Откройте `https://<сайт>/api/health`. Должно быть:


  1. Снять копию:

     ```bash
     DATABASE_URL='postgresql://…строка Pooled из ONREZA…' node scripts/db-backup.mjs
     ```

     Скрипт напишет файл `inflatia-backup-<дата>.jsonl.gz` и числа строк по таблицам — сверьте с числом ключей на сайте

  2. Проверить файл (целостность и хэши): `node scripts/db-backup.mjs --check inflatia-backup-….jsonl.gz`.

     ```bash
     RESTORE_URL='postgresql://…строка ВЕТКИ…' node scripts/db-backup.mjs --restore inflatia-backup-….jsonl.gz
     ```

     «Развёрнуто и сверено: копия проверена» — это и есть проверенная копия. Ветку после проверки удалите.
  4. Копия Upstash и сравнение (перед удалением Upstash):

     ```bash
     KV_REST_API_URL='…' KV_REST_API_TOKEN='…' node scripts/db-backup.mjs --upstash
     node scripts/db-backup.mjs --compare upstash-backup-….jsonl.gz inflatia-backup-….jsonl.gz
     ```

     Значения не выводятся — только число ключей по префиксам: каких нет в ONREZA и у каких значение другое (у активных
     учеников значения в ONREZA новее — это нормально). Короткоживущие ключи (`session:`, `hit:`, `link:`, `cnt:`) могут
     отличаться.
- Файлы копий — персональные данные: хранить зашифрованными (архив с паролем или зашифрованный диск), не в репозитории
  (`.gitignore` их не пропустит) и не в облаке без шифрования. Копии, снятые во время сбора исследования, удалить в день
  фиксации набора (`research/retention-policy.md`, раздел 4).
- Стандартный `pg_dump` по той же строке тоже подходит (`pg_dump` версии не ниже сервера).

- **Журналы ONREZA.** Что база пишет в журналы подключений и сколько их хранит — в документации не нашёл; спросить у
  поддержки ONREZA и записать в `docs/data-architecture.md`, раздел 7.
- **Права базы.** Пользователь базы один на обе таблицы. Отдельных SQL-логинов с ограниченными правами управляемый PostgreSQL
  ONREZA не даёт (docs.onreza.ru → PostgreSQL → «Роли и доступ из Functions»: «Создание отдельных SQL-логинов с
  ограниченными правами в панели управления не предусмотрено»), поэтому разделение таблиц держится в коде
  (`api/_lib/research-store.js` видит только `inflatia_research`).
