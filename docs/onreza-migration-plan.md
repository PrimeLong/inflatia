# План перехода Инфляции с Upstash Redis на PostgreSQL ONREZA

Составлено 21.11.2026 по запросу владельца: аудит, целевая архитектура, файлы, инструкции владельцу и разработчику, риски,
оценки и критерии готовности. Юридических выводов здесь нет: что считать персональными данными и достаточно ли
локализации — вопрос к юристу (`docs/legal-todo.md`, п. 1–5). Подробный перечень полей — `docs/data-architecture.md`;
команды переноса — `docs/onreza.md`.

> **Важно: первая часть переноса уже сделана.** 20.11.2026 по сообщению владельца «Можешь сам перейти на Onreza, вот
> ключ» рабочий сайт переключён на PostgreSQL ONREZA: все 2545 ключей Upstash скопированы, `DATABASE_URL` задан для
> Production, `/api/health` отвечает `{"db":"postgres","region":"arn1"}`. Upstash **не тронут** — в нём осталась копия
> данных на 20.11, туда больше не пишется. Поэтому этот план описывает: что уже сделано (этап 1, «Перенос как есть»);
> что можно улучшить (этап 2, «Настоящие таблицы»); и как откатиться. Ничего необратимого без отдельного подтверждения
> владельца не делается: Upstash не удаляется, схема `inflatia_kv` не меняется.

## 2. Целевая архитектура

### 2.1. Решение по исследовательской базе

> **Сделано 22.11.2026** по решению владельца: одна база `DATABASE_URL`, исследование — в своей таблице
> `inflatia_research` (не в схеме `research` со своим пользователем: строка подключения одна, разделение — в коде, мост
> к аккаунтам — `api/_lib/research-link.js`). Связь «логин ↔ код» — только где нужна методике (протокол 0.4).
> Описание — `docs/onreza.md`, `research/data-dictionary.md`, раздел 1. Ниже — исходное предложение 21.11.

Владелец 21.11: **одна общая база для всей Инфляции, без отдельной исследовательской базы.** Сейчас код и документы
исследования (`research/protocol.md`, `research/data-dictionary.md`, `api/_lib/research-store.js`) требуют отдельную
базу: это было сделано, чтобы исследовательские данные физически не смешивались с аккаунтами и выгрузка не могла
захватить логины. Предлагаемая замена — **одна база ONREZA, но отдельная схема PostgreSQL `research`** и отдельный
пользователь базы для неё:

- таблицы исследования — в схеме `research`, таблицы аккаунтов — в `public`;
- обработчик `api/research.js` подключается **своим пользователем базы** (`RESEARCH_DATABASE_URL` с логином `inflatia_research`),
  у которого есть права только на схему `research` — даже ошибка в коде не даст ему прочитать `public.users`;
- код аккаунтов (`store.js`) прав на схему `research` не имеет.

Это одна база (один счёт, одна копия, одно место размещения), но с той же изоляцией, что давали две базы. Нужно
обновить `research/data-dictionary.md` («Где хранится») и `research/protocol.md`; исследование при этом остаётся закрытым
(`STUDY_STATUS = 'draft'`) — открывается только по порядку из протокола. Если пользователя базы с ограниченными правами на
тарифе ONREZA создать нельзя (уточнить в панели, §4.2) — запасной вариант: та же база, отдельная схема, без своего
пользователя; изоляция тогда только в коде, и это нужно честно написать в протоколе.

### 2.2. Этап 1 — «перенос как есть» (сделан 20.11)

Одна таблица `inflatia_kv (k text, f text, v jsonb, exp bigint, PRIMARY KEY (k, f))` и частичный индекс по сроку. Адаптер
`api/_lib/pgkv.js` выполняет те команды Redis, которыми пользуется сервер; атомарные операции (`incr`, `set nx`,
`rpush`) — одной командой SQL. Плюсы: ни один обработчик не менялся, весь функционал сохранён, откат — одной переменной.
Минусы: связи между пользователем и его данными не проверяются базой (это строки с ключами, как в Redis); профиль
пользователя — один JSON, и два одновременных изменения друзей могут затереть друг друга (так же было и в Redis); нет
внешних ключей и ограничений.

Что это даёт: удаление аккаунта каскадом стирает всё связанное (сейчас — перечнем ключей в `deleteUserData`, и, например,
логин в списках друзей у других остаётся до их обращения); дружба хранится одной строкой на пару, а не в двух
JSON-профилях — одновременные заявки больше не затирают друг друга; база сама не даст записать мусор (логин не того
вида, ссылку на несуществующего пользователя); жалобы и таблицы читаются запросами, а не целиком.

**Сессии.** Сейчас ключ входа хранится в базе как есть (`session:<токен>`). В таблице `sessions` предлагается хранить
**SHA-256 от токена**: утечка копии базы тогда не даёт войти чужими сессиями. Старые сессии переносятся с хэшированием
токена — ученики не разлогиниваются. Эпоха пароля остаётся: смена пароля гасит все старые сессии.

**Пароли и восстановление.** Остаются **scrypt** с солью (хэш и соль переносятся как есть — пароли учеников продолжают
подходить, повторно задавать их не нужно). Код восстановления — тоже хэш scrypt. Почты нет, восстановление — только кодом,
как сейчас.

**Конкурентные запросы.** Изменения, которые касаются двух записей (дружба, забег, распределение в исследовании) —
в транзакции; запись профиля ученика — `UPDATE … WHERE updated_at = $prev` (оптимистичная блокировка) или
`SELECT … FOR UPDATE`. Счётчики — `INSERT … ON CONFLICT DO UPDATE SET n = n + 1`. Пул соединений — режим **Pooled** ONREZA
(PgBouncer) и не больше 3 соединений на экземпляр функции (уже так, `poolFrom`).

**Миграции схемы.** Папка `db/migrations/NNN_описание.sql`, таблица `schema_migrations`, скрипт `scripts/db-migrate.mjs`
применяет новые файлы по порядку в одной транзакции. Запуск — вручную владельцем со своего компьютера или
разработчиком через одноразовый защищённый адрес, как 20.11 (сеть разработчика до базы не достаёт). Не на каждой сборке:
сборка не должна менять рабочую базу.

**Резервное копирование.** Основное — средства ONREZA (восстановление на момент времени, PITR, и независимая копия; по их
документации — в Санкт-Петербурге, §5). Дополнительно — ручная выгрузка `pg_dump` владельцем раз в неделю на свой
компьютер и **перед каждой миграцией схемы**. Через GitHub Actions копии не делать: копия базы ушла бы на серверы GitHub.

**Как перенести данные на этапе 2.** Без внешних машин: данные уже в той же базе, перенос — SQL-скриптом
`db/migrations/002_from_kv.sql` из `inflatia_kv` в новые таблицы. `inflatia_kv` при этом **не удаляется** — это копия
для отката. Код переключается на новые таблицы флагом `DB_SCHEMA=v2`: без флага — старая таблица.

1. ONREZA → база → **Подключение** (или **Пользователи**) → **Сбросить пароль** → скопируйте новую строку Pooled.

3. **Upstash не удалять** до отдельного решения (§6.8).

## 6. Безопасность и сохранность данных

1. **Резервная копия Upstash перед миграцией.** Отдельной выгрузки 20.11 не делалось. Роль копии сыграл сам Upstash: при
   переносе он только читался и сейчас хранит данные на момент переключения. Выгрузка в файл — §4.6 (нужен
   `scripts/kv-dump.mjs`, §7.5).
2. **Полнота переноса.** 20.11 сверено число ключей: Upstash 2545 = PostgreSQL 2545, по видам string 2540, hash 3, set 2;
   догоняющий проход новых ключей не нашёл. **Сверку значений по каждому ключу** (контрольная сумма JSON) предлагаю
   сделать на этапе 7.5 — до любого удаления Upstash.
3. **Пароли и сессии.** Переносятся соль и хэш scrypt как есть, ключи входа — как есть: после переключения ученики не
   разлогинились, пароли подходят. Проверка — §4.8, п. 2–3, и тесты `api/__tests__/account.test.js`, `security.test.js`
   на обеих базах.
4. **Регистрация и вход** — e2e и `account.test.js`; вручную — §4.8.
5. **Прогресс, достижения, друзья, чат** — `progress.test.js`, `friends.test.js`, `room.test.js`, e2e «Друзья», «Шахта v2»,
   «Сетевая комната».
6. **Откат.** Сейчас: удалить `DATABASE_URL` (Production) и Redeploy — сайт вернётся на Upstash. **Но** всё, что ученики
   записали с 20.11, есть только в ONREZA. Поэтому перед откатом нужен обратный перенос `scripts/pg-to-upstash.mjs`
   (§7.6), иначе откат потеряет прогресс за эти дни. На этапе 2 откат — флаг `DB_SCHEMA=v1`: старая таблица
   `inflatia_kv` остаётся, а для обратной совместимости код v2 первые две недели пишет в обе схемы.
7. **Без потерь при переключении.** Сделано так: перенос → переключение → догоняющий перенос только отсутствующих ключей
   (`--missing`, свежие данные не затираются). Окно, когда запись могла уйти в старую базу, — время пересборки (~40 с);
   догоняющий проход их подобрал (нашёл 0).
8. **Отключение старой инфраструктуры** — только после: отдельного подтверждения владельца; сверки значений (п. 2);
   выгрузки Upstash в файл (§4.6); двух недель работы на ONREZA без ошибок; решения юриста о копии в США. Тогда:
   **Vercel → Storage → база → Settings → Delete** и удалить переменные `KV_*`/`REDIS_URL`. Сейчас — **не делать**.
