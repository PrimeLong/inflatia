# Переезд на ONREZA

Пошаговая инструкция переноса сайта с Vercel на ONREZA Platform (onreza.ru). Сведено по документации ONREZA
(docs.onreza.ru, полная версия — docs.onreza.ru/llms-full.txt) на 18.11.2026. Юридических выводов здесь нет: нужна ли
локализация данных в России и чего она требует — вопрос к юристу (`docs/legal-todo.md`, п. 1–2).

## Как это устроено после переезда

| Что | На Vercel | На ONREZA |
|---|---|---|
| Страницы, скрипты, музыка, картинки (`dist/`) | CDN Vercel | **STATIC-слой** — CDN ONREZA |
| Серверная часть `api/*.js` | Vercel Functions: каждый файл — функция `handler(req, res)` | **COMPUTE-слой** — один Node-процесс `server/onreza.mjs`: те же `req` и `res`, адрес `/api/<имя>` → `api/<имя>.js` |
| Адреса SPA (`/book`, `/shop`, …) и заголовки безопасности (CSP и др.) | `vercel.json` | `onreza.rules.toml` (Edge Rules) — то же, слово в слово |
| База | Upstash Redis, регион `iad1` (США) | **Пока та же база Upstash** (этап 1). Перенос в ONREZA — этап 2 ниже |

Почему не ONREZA Functions: в бета-версии функция — один самодостаточный файл до 128 КБ без npm-зависимостей и без
импортов из других файлов; у нас восемь обработчиков с общим кодом и клиентом `@upstash/redis`. Compute — обычный
Node.js-процесс, код API в нём работает без переделки.

### Что уже сделано в репозитории

- `server/onreza.mjs` — сервер API для Compute: слушает `PORT` на `0.0.0.0`, даёт обработчикам `req.query`, разобранный
  JSON в `req.body`, `res.status().json()` — как Vercel. Неизвестный адрес — 404, падение обработчика — 500 без подробностей,
  тело больше 4,5 МБ — 413. Проверочный адрес `/api/_health` (см. шаг 5).
- `scripts/onreza-pack.mjs` и команда `npm run build:onreza` — собирают папку `.onreza-out`: `site/` (копия `dist`),
  `server/server.mjs` (API одним файлом со всеми зависимостями) и `.onreza/manifest.json` (манифест: `/api/*` → Compute,
  остальное → STATIC). Код сервера лежит отдельно от `site/` и в публичную раздачу не попадает.
- `onreza.rules.toml` — переписывание адресов SPA на `index.html` (существующие файлы важнее правила) и заголовки
  безопасности из `vercel.json`.
- `onreza.toml` — команда сборки, папка результата, список переменных окружения.
- Номер сборки в «Сообщить об ошибке» берётся из `ONREZA_GIT_COMMIT_SHA`, как раньше из `VERCEL_GIT_COMMIT_SHA`.
- Проверка — `api/__tests__/onreza.test.js`: сервер отвечает как Vercel, каждый файл `api/` подключён, правила совпадают
  с `vercel.json`, сборка раскладывает файлы правильно.

`vercel.json` не удалён: пока Vercel не отключён, сайт работает и там.

## Этап 1. Сайт на ONREZA, база прежняя

### Шаг 1. Аккаунт

1. Откройте **app.onreza.ru** и войдите через **GitHub** (тот же аккаунт, где репозиторий). При первом входе создаётся
   личное рабочее пространство (workspace).
2. **Workspace → Settings → Git → Install GitHub App** — выберите только репозиторий `PrimeLong/inflatia`
   (доступ ко всем репозиториям не нужен).

### Шаг 2. Проект из репозитория

1. **Создать проект → GitHub** → `PrimeLong/inflatia`, ветка production — `main`.
2. В **Build Settings** замените то, что определилось само (автодетект увидит Vite и предложит только статику):

   | Поле | Значение |
   |---|---|
   | Framework Preset | **Other** |
   | Install Command | `npm ci` |
   | Build Command | `npm run build:onreza` |
   | Output Directory | `.onreza-out` |
   | Node.js | **22** |

   Для Git-деплоя ONREZA берёт команду и папку из этих настроек, а не из `onreza.toml` — поэтому их нужно ввести здесь.
3. Пока не нажимайте «Deploy» — сначала переменные (шаг 3), иначе первая сборка поднимется без базы.

### Шаг 3. Переменные окружения

Перенесите значения из **Vercel → проект → Settings → Environment Variables** в **ONREZA → проект → Settings →
Environment Variables**. Ключи и пароли отмечайте как **секрет** (их потом нельзя прочитать — только заменить).

| Переменная | Что это | Окружения | Секрет |
|---|---|---|---|
| `KV_REST_API_URL` | адрес базы Upstash | Production и Preview | да |
| `KV_REST_API_TOKEN` | ключ базы Upstash | Production и Preview | да |
| `OWNER_LOGINS` | логины владельца (разбор жалоб), через запятую | Production и Preview | нет |
| `RESEARCH_STATUS` | статус исследования; пока не задан — исследование закрыто | только если задан на Vercel | нет |
| `RESEARCH_KV_REST_API_URL`, `RESEARCH_KV_REST_API_TOKEN` | отдельная база исследования | только если уже созданы | да |
| `RESEARCH_EXPORT_TOKEN`, `RESEARCH_ALLOC_SEED` | ключ выгрузки и зерно распределения | только если уже заданы | да |

Важно: в Vercel значения базы Upstash подставляла сама интеграция Marketplace. Чтобы увидеть их, откройте
**Vercel → Storage → база → `.env.local`** (кнопка Show secret) или консоль Upstash (**Open in Upstash → REST API**).

Если хотите, чтобы превью-развёртывания (ветки и PR) не писали в рабочую базу, задайте для **Preview** адрес и ключ
другой, пустой базы Upstash. Иначе превью работает с теми же аккаунтами, что и сайт.

### Шаг 4. Первая сборка и проверка на адресе ONREZA

1. Нажмите **Deploy**. В логе сборки должно быть: `vite build` без ошибок и строка `ONREZA: .onreza-out готова`.
2. ONREZA выдаст адрес вида `https://<проект>-<workspace>.onreza.app`. Проверьте на нём:
   - главная открывается, урок проходится, музыка играет;
   - **обновите страницу на `/shop`, `/book`, `/book/<глава>`, `/world`** — должна открыться та же страница, а не 404
     (это правила SPA из `onreza.rules.toml`);
   - вход в аккаунт и сохранение прогресса работают (значит, API видит базу);
   - «Сообщить об ошибке» отправляется и видно в разборе жалоб у владельца.
3. Заголовки безопасности — с компьютера:

   ```bash
   curl -sI https://<адрес>.onreza.app/ | grep -i -E "content-security-policy|x-frame-options|referrer-policy"
   ```

   Должны быть все три строки. Если их нет — правила из репозитория не подхватились: опубликуйте их вручную
   (**проект → Edge Rules**, вставить содержимое `onreza.rules.toml`, или `nrz rules publish` из CLI).

### Шаг 5. Проверка сервера API

Откройте `https://<адрес>.onreza.app/api/_health`. Ответ должен быть таким:

```json
{"ok":true,"kv":true,"forwardedFor":true,"commit":"…"}
```

- `kv: false` — не заданы `KV_REST_API_URL`/`KV_REST_API_TOKEN` для этого окружения (шаг 3), сайт работает «в памяти»,
  и всё сохранённое пропадёт при перезапуске процесса.
- `forwardedFor: false` — ONREZA не передала серверу адрес клиента. Тогда ограничение «не больше 30 попыток входа в час
  с одного адреса» (`api/account.js`) и лимит жалоб (`api/reports.js`) считаются **на всех пользователей сразу**. Сайт
  работает, но при наплыве вход может закрыться для всех на час. Напишите мне — переделаю лимиты под заголовок,
  который передаёт ONREZA (уточнить в поддержке ONREZA, каким заголовком приходит IP).
- Сам IP-адрес этот ответ не показывает.

### Шаг 6. Свой домен

1. **Проект → Domains → Add** — введите домен сайта.
2. Выберите способ:
   - **Делегирование** (рекомендует ONREZA) — у регистратора домена поменять NS-серверы на указанные ONREZA;
   - **Внешний DNS** — оставить DNS у регистратора и добавить TXT-запись подтверждения и CNAME (для домена без `www` —
     ALIAS/ANAME или A-запись на IPv4, который покажет ONREZA).
3. Сертификат HTTPS ONREZA выпускает сама после проверки DNS. Пока DNS не переключился, сайт продолжает открываться
   с Vercel — простоя нет.
4. Если почта на домене есть — при делегировании перенесите MX-записи в DNS ONREZA до смены NS.

### Шаг 7. Отключение Vercel

1. Подождите неделю после переключения домена: проверьте, что жалобы приходят, аккаунты и сохранения работают.
2. В Vercel: **Settings → Git → Disconnect** (чтобы пуши не собирались в двух местах), затем удалите домен из проекта.
3. **Базу Upstash в Vercel не удаляйте** — на этапе 1 ONREZA работает с ней же. Интеграция Vercel ↔ Upstash
   при удалении проекта может удалить и базу: сначала этап 2 или перенос базы в отдельный аккаунт Upstash.
4. После этого `vercel.json` можно удалить; но `vite.config.ts` читает из него заголовки для `vite preview` (e2e) —
   перед удалением попросите меня перенести их в общий файл.

### Если что-то пошло не так

- Сборка не прошла — **Deployments → сборка → Logs**; самые частые причины: не та папка результата (нужно
  `.onreza-out`) или Node ниже 22.
- Откат — **Deployments → предыдущий успешный → Rollback**: возвращает и сайт, и правила.
- Домен ещё на Vercel — достаточно не трогать DNS, сайт работает как раньше.

## Этап 2. База в ONREZA (по решению)

На этапе 1 данные аккаунтов, сохранений, жалоб и исследования остаются в Upstash в США (`iad1`,
`docs/data-architecture.md`). Сам переезд хостинга их место хранения не меняет. Если цель переезда — хранить данные в
России (ONREZA пишет, что её инфраструктура — дата-центры Selectel в Санкт-Петербурге, Ленинградской области и Москве;
docs.onreza.ru → «Размещение данных и сведения для РКН»), нужен второй этап:

- **KV ONREZA не подходит как есть.** Он доступен только из ONREZA Functions (`ctx.kv`), из Compute — нет; и у него
  шесть операций (get/set/incr/delete/list), а код использует ещё хеши, множества, `mget`, `scan`.
- **Подходит управляемый PostgreSQL ONREZA**: создаётся в разделе **PostgreSQL**, подключается к проекту как интеграция —
  тогда в процесс приходит `DATABASE_URL`. Нужна работа в коде: `api/_lib/store.js` и `api/_lib/research-store.js`
  переводятся с Redis на таблицы PostgreSQL (те же операции, с истечением срока), плюс разовый скрипт переноса
  данных из Upstash. Отдельная база исследования — отдельная база PostgreSQL (п. 7 из замечаний 18.11).
- Что решить до этапа 2: нужен ли он (юрист); какой тариф (на Hobby ONREZA не даёт подписываемых поручений обработки
  персональных данных — «Документы и Hobby» в их документации); когда делать перенос (нужен короткий режим «только
  чтение» на время копирования).

## Отличия, о которых стоит знать

- **Холодный старт.** Compute на ONREZA засыпает без трафика (scale-to-zero); первый запрос после паузы ждёт запуска
  процесса (до нескольких секунд). Сайт и уроки открываются сразу — с CDN; задержка только у первого обращения к API.
- **Превью.** Каждая ветка и PR получают свой адрес, как на Vercel.
- **Письма** из Compute по SMTP отправлять нельзя (порты закрыты) — у нас писем нет.
- **Журналы.** Логи сборки и процесса — в карточке развёртывания. Что ONREZA пишет в журнал запросов (IP, User-Agent)
  и сколько хранит — в документации не нашёл; спросить у поддержки ONREZA и записать в `docs/data-architecture.md`.
