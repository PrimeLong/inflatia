# Словарь исследовательских данных

К [протоколу](protocol.md) версии 0.4. Это **полный** перечень того, что исследование может хранить. Источник для кода — `src/research/dictionary.js`; тест `src/research/__tests__/research.test.js` сверяет этот документ с кодом: поле, которого нет здесь, сервер не примет.

Главное правило: **исследовательский набор собирается отдельно** — своей целью, своей таблицей и своими правами доступа, только у записавшихся участников и только после запуска. База при этом **одна** — та же PostgreSQL ONREZA, что у Инфляции (решение владельца 22.11.2026, `docs/onreza.md`).

## 1. Две разные обработки в одной базе

| | А. Обычная работа Инфляции | Б. Исследование |
|---|---|---|
| Цель | Учиться, сохранять прогресс, играть, общаться с друзьями | Проверить гипотезы [протокола](protocol.md) и написать отчёт |
| Кто | Любой пользователь | Только записавшиеся совершеннолетние участники с аккаунтом Инфляции |
| Основание участия | Регистрация (или без неё) по документам Инфляции | Отдельное согласие на странице исследования |
| Как узнаём человека | Логин, ключ входа, `playerId` | В записях — только случайный код участника; связь «аккаунт ↔ код» — одной служебной парой (раздел 2, «Связь с аккаунтом») |
| Где хранится | PostgreSQL ONREZA (`DATABASE_URL`), таблица `inflatia_kv` — `docs/data-architecture.md` | **Та же база**, отдельная таблица `inflatia_research` |
| Код сервера | `api/account.js`, `api/_lib/store.js` и др. | только `api/research.js` и `api/_lib/research-store.js`; мост к аккаунтам — `api/_lib/research-link.js` |
| Что входит | Регистрация, вход, прогресс, монеты, друзья, достижения, сетевая игра | Сбор показателей, сравнение групп, статистика, отчёт |
| Срок хранения | По документам Инфляции | [retention-policy.md](retention-policy.md) |

### Права доступа — кто что может

Одна база не значит общий доступ. Разделение держится в коде (проверяют тесты `api/__tests__/research.test.js` и `api/__tests__/account.test.js`):

| Кто | Таблица `inflatia_kv` (Инфляция) | Таблица `inflatia_research` (исследование) |
|---|---|---|
| Код Инфляции (`store.js`, `account.js`, `room.js` и др.) | читает и пишет | не обращается — кроме двух действий самого человека через мост `research-link.js`: «Удалить аккаунт» стирает его участие (как отзыв), «Скачать мои данные» отдаёт ему его же записи исследования |
| Код исследования (`research.js`, `research-store.js`) | не обращается; по ключу входа через мост узнаёт **только логин и год рождения** — ничего не пишет и больше ничего не читает | читает и пишет только поля этого словаря |
| Ответственный исследователь | нет | выгрузка (`export`) и удаление набора (`purge`) — только по ключу `RESEARCH_EXPORT_TOKEN`; в выгрузке нет логинов и связи с аккаунтами |
| Владелец Инфляции как администратор | разбор жалоб и счётчики — через приложение (`OWNER_LOGINS`) | через приложение — нет; доступ к базе целиком (строка подключения) у владельца есть технически — это записано как остаточный риск в `docs/data-architecture.md` |

Отдельного пользователя базы с правами только на одну таблицу сейчас нет (строка подключения одна); если ONREZA позволит завести второго пользователя, таблицу исследования можно закрыть и на уровне базы — без изменений в этом словаре.

## 2. Поля исследовательского набора

### Таблица `participants` — по строке на участника

| Поле | Тип и значения | Зачем исследованию |
|---|---|---|
| `participant_code` | случайный код вида `K7QM-2XRT-9H` | Связать занятия, тесты и ответы одного участника без логина и аккаунта; по нему же участник отзывает участие |
| `protocol_version` | строка версии | Знать, по какой версии протокола собраны данные |
| `consent_version` | строка версии | С каким текстом информации для участника он согласился |
| `adult_confirmed` | да | Критерий включения пилота — только совершеннолетние; без отметки запись не принимается |
| `period` | месяц `ГГГГ-ММ` | Период проведения без даты и времени: описание исследования, проверка, не сместились ли группы во времени |
| `stratum` | `low` / `high` | Слой по входному тесту, внутри которого шло распределение; учитывается в анализе |
| `arm` | `game` / `plain` | Экспериментальная группа — основное сравнение |
| `material_version` | строка версии сборки | Какую версию модуля проходил участник; обе группы должны проходить одну |
| `stage` | `enrolled` → `pretest` → `material` → `posttest` → `delayed` | Докуда дошёл участник — для схемы потока участников и анализа выбывания |
| `used_regular_app` | `no` / `yes` / `unsure`, необязательно | Пользовался ли участник обычной Инфляцией во время исследования — проверка смешения групп |
| `form_order` | `AB` / `BA` | Порядок форм входного и итогового тестов, назначенный сервером случайно при записи, — чтобы различие форм не совпало с этапом и его можно было учесть в анализе |

**Служебное поле (хранится в таблице исследования, в выгрузку не идёт):**

| Поле | Тип и значения | Зачем |
|---|---|---|
| `enrolled_on` | дата `ГГГГ-ММ-ДД`, **без времени** | Серверу — считать день исследования и проверять окна тестов. Точного времени записи в базе нет. Удаляется вместе с базой при фиксации набора ([retention-policy.md](retention-policy.md), раздел 2) |

Иначе говоря: **в наборе для анализа** нет ни дат, ни времени (только день исследования и месяц); **в рабочей базе** до фиксации набора есть одна дата на участника — день записи — и больше никаких отметок времени.

### Таблица `events` — события обучения в исследовательском режиме

| Поле | Тип и значения | Зачем исследованию |
|---|---|---|
| `participant_code` | код участника | Чьё событие |
| `study_day` | целое 0–60 | День исследования от записи вместо даты и времени — число активных дней, сроки этапов |
| `session_no` | целое 1–200 | Номер занятия — сколько раз участник возвращался; ставит сервер |
| `event_type` | `session_start`, `lesson_start`, `lesson_done`, `exercise_answer` | Что произошло. Клиент сообщает только `session_start` и `lesson_start`; `exercise_answer` и `lesson_done` пишет сервер |
| `lesson_id` | id урока, например `hh-l1` | Доля пройденных уроков, сравнение уроков |
| `task_no` | целое 1–99 | Номер задания в уроке; ставит сервер по модулю |
| `exercise_id` | id задания | Какое задание (одинаковое в обеих группах) — трудность заданий |
| `correct` | да/нет | Правильность ответа — считает сервер по сырому ответу и ключу модуля (`src/research/module.js`), не клиент |
| `attempt_no` | целое 1–99 | Номер попытки — «верно с первой попытки» и число попыток; считает сервер |
| `active_seconds` | целое 0–7200 | Активное время — продолжительность обучения; считает сервер по своим часам: промежуток с прошлого действия участника, простой дольше 3 минут не входит. У `lesson_done` — сумма по уроку |

### Таблица `tests` — ответы на задачи тестов знаний

| Поле | Тип и значения | Зачем исследованию |
|---|---|---|
| `participant_code` | код участника | Чей тест |
| `test_kind` | `pre` / `post` / `delayed` | Входной, итоговый или отсроченный — основа сравнения усвоения и закрепления |
| `form` | `A` / `B` / `C` | Параллельная форма — учесть различия форм по трудности |
| `item_id` | id задачи теста | Надёжность теста и трудность задач |
| `correct` | да/нет | Балл задачи 0/1 — считает сервер по ключу ответов (`api/_lib/research-key.js`, на страницу не попадает); клиент присылает только ответы |
| `study_day` | целое 0–60 | Проверить, что тест пройден в своём окне |
| `test_seconds` | целое 0–14400 | Сколько длился весь тест по часам сервера (от выдачи задач до отправки) — отличить попытку решения от ответа наугад |

### Связь с аккаунтом — только где нужна методике

Пара служебных ключей на участника в таблице `inflatia_research`: `rla:<логин>` → код участника и `rlc:<код>` → логин. Других полей нет; в записи `participants`, `events`, `tests` логин не попадает (`login` по-прежнему запрещённое поле — раздел 3), в выгрузку для анализа связь не идёт.

| Зачем методике ([методика](methodology.md), раздел 8) | Как используется |
|---|---|
| Один человек — одно участие: повторная запись под новым кодом исказила бы выборку и позволила бы «перевыбрать» группу | При записи сервер проверяет, нет ли у аккаунта кода; две одновременные записи одного аккаунта дают одного участника |
| Критерий включения 18+ | Год рождения аккаунта: если по году участнику меньше 18, запись не принимается даже с отметкой «мне 18». Год **не сохраняется** в исследовании |
| Выбывание — главный показатель пилота: потерянный код раньше означал выбывание | На другом устройстве участник входит в аккаунт и продолжает («Продолжить с аккаунтом») |
| Права участника не должны расходиться с правами пользователя | «Удалить аккаунт и все данные» стирает и участие (как отзыв, до фиксации набора); «Скачать мои данные» включает свои записи исследования |

Связь стирается при отзыве участия, при удалении аккаунта и при фиксации набора — вместе со всеми ключами исследования ([retention-policy.md](retention-policy.md)). Чего связь **не** даёт: прогресс, монеты, друзья, лиги, жалобы и любые другие данные аккаунта в исследование не идут; проверка «проходили ли вы „Сберкассу“» остаётся вопросом участнику, по прогрессу аккаунта не делается.

**Отдельно**, без привязки к данным участника: число отозвавших участие (`rwithdrawn`) — для схемы потока участников; счётчики распределения по слоям (`rcount:<слой>`) и номер участника в слое (`rslot:<код>`) — чтобы назначение было атомарным и воспроизводимым по зерну; короткая блокировка на время входного теста (`rlock:<код>`, живёт 30 секунд); число записавшихся за день (`rday:<дата>`, защита от массовой записи). **Служебный ход по модулю** (`rx:<код>:…`), который ведёт сервер, чтобы не верить клиенту: счётчики попыток заданий, отвеченные задания и пройденные уроки (день прохождения), активные секунды урока, номер занятия — и две короткоживущие отметки времени сервера: последнее действие (живёт 30 минут) и выдача задач теста (живёт 4 часа, стирается при отправке). В выгрузку `rx:` не идёт и стирается при отзыве участия. Сами ответы участника (что он ввёл) не хранятся — только «верно / неверно». Всё это удаляется при фиксации набора (действие `purge` стирает все ключи таблицы исследования).

## 3. Чего в наборе нет

Сервер отклоняет запись целиком, если в ней есть такое поле под любым из написаний (`forbiddenField` в `src/research/dictionary.js`):

| Группа | Под какими именами ловится | Почему исследованию не нужно |
|---|---|---|
| login | login, username, user | Логин указывает на аккаунт; данные связывает код участника, а связь с аккаунтом — отдельная служебная пара (раздел 2) |
| password | password, pass, hash, salt, recHash, recSalt | Пароли и их хэши нужны только входу в аккаунт |
| recoveryCode | recoveryCode, recovery, rec | Коды восстановления нужны только входу |
| token | token, session, authorization, auth, cookie | Токены авторизации нужны только входу |
| ip | ip, x-forwarded-for, remoteAddress | Сетевой адрес не нужен ни одному показателю |
| parentName | parentName, parent | Пилот — только совершеннолетние |
| chat | chat, messages, message, comment, text | Переписки и свободный текст могут содержать что угодно о человеке; исследование их не анализирует |
| friends | friends, fin, fout, races | Социальные связи — часть обычной работы Инфляции |
| playerId | playerId, accountId, userId, profileId, deviceId | Технический идентификатор соединил бы записи с прогрессом и сохранениями аккаунта |
| name | name, nickname, nick, email, phone, birthYear, emblem | Не нужны показателям; совершеннолетие — отдельной отметкой |
| userAgent | userAgent, ua, device, viewport | Помогают узнать устройство, не входят в показатели |
| timestamp | timestamp, at, time, date, createdAt | Точное время заменено днём исследования и месяцем |

Чего нет и **не будет без новой версии протокола**: других данных аккаунта, кроме пары связи (раздел 2), анкет самоотчёта, данных о монетах, покупках, друзьях и лигах участника, текста ответов (только «верно/неверно»).

## 4. Псевдонимизация — не анонимность

Код участника не содержит сведений о человеке, но **набор с кодами — псевдонимизированный, а не анонимный**: код хранится на устройстве участника, а до фиксации набора в той же базе есть пара связи «код ↔ логин». Поэтому, пока коды и связь существуют, исследовательские данные считаются данными о конкретных людях и защищаются соответственно (доступ — только у исследования, своя таблица, сроки — [retention-policy.md](retention-policy.md)). Квалификацию этих данных по закону даёт правовая проверка ([протокол](protocol.md), п. 11), а не этот документ.

Чтобы уменьшить риск узнавания и в псевдонимизированном наборе: в наборе для анализа нет дат и времени (только день исследования и месяц; в рабочей базе — только дата записи, без времени), нет логина, устройства и адреса, нет свободного текста, в отчёте — только группы, группы меньше 5 человек не детализируются. Связь с аккаунтом стирается в день фиксации — после неё набор не связан ни с кем.

## 5. Где хранится и кто видит

- База одна — PostgreSQL ONREZA (`DATABASE_URL`; по сведениям ONREZA — Санкт-Петербург), записи исследования — в своей таблице `inflatia_research`. Отдельная переменная `RESEARCH_DATABASE_URL` и отдельная база не нужны. Без `DATABASE_URL` (локально, превью) исследование закрыто.
- Запись — только через `api/research.js` и только поля словаря; связь с аккаунтом — только через `api/_lib/research-link.js` (раздел 1, «Права доступа»).
- Выгрузка — только по ключу `RESEARCH_EXPORT_TOKEN`, который есть только у ответственного исследователя; выгрузка содержит только поля словаря, без связи с аккаунтами.
- Регион базы, журналы платформ и резервные копии — см. [retention-policy.md](retention-policy.md), раздел 4, и `docs/data-architecture.md`.
- **Инфраструктурные провайдеры.** До переноса сервера в ONREZA Compute (подготовлен, не включён — `docs/onreza.md`) запросы участника обрабатывают функции Vercel (Стокгольм) — хостинг видит и пишет в свои журналы IP-адрес и строку браузера; это не исследовательские данные, исследование их не получает и не связывает с кодом участника, но провайдер их видит — это сказано участнику ([информация для участника](participant-information.md), «Что видят технические провайдеры»).

## 6. Служебные ключи сервера (не входят в набор для анализа)

Ход участника по модулю сервер ведёт в ключах `rx:<код>:…` таблицы `inflatia_research`: `start:<урок>` — когда сервер записал
«начал урок» (без этой отметки ответы на задания урока не принимаются), `seen:<задание>` и `cnt:<урок>` — на какие задания
уже был ответ (ответ на задание k принимается после ответов на 1…k−1), `att:<задание>` — номер попытки, `sec:<урок>`,
`last` — активное время, `issue:<тест>` — когда выданы задачи теста, `done:<урок>` — урок пройден. В выгрузку они не идут
и стираются вместе с участником (отзыв, «Удалить аккаунт») и при удалении набора. Ключ ответов модуля и теста — в коде
сервера (`api/_lib/research-module-key.js`, `api/_lib/research-key.js`), не в базе и не в браузере.
