## Как это устроено

| Что | Где |
|---|---|
| Страницы, скрипты, музыка, картинки | Vercel (сеть узлов по миру) |
| Серверные функции `api/*.js` | Vercel, `arn1` — Стокгольм |
| База аккаунтов, прогресса, жалоб и всего остального | **PostgreSQL ONREZA**, таблица `inflatia_kv` — переменная `DATABASE_URL` |
| Исследование | **та же база**, таблица `inflatia_research` (своя цель и свои права доступа — `research/data-dictionary.md`, раздел 1) |
| Старая база | Upstash Redis, `iad1` (США) — копия на 20.11, не используется рабочим сайтом |

ONREZA пишет, что её инфраструктура — дата-центры Selectel в Санкт-Петербурге, Ленинградской области и Москве
(docs.onreza.ru → «Размещение данных и сведения для РКН»); основное хранилище PostgreSQL и резервные копии — Санкт-Петербург.

### Что сделано в коде

- `api/_lib/pgkv.js` — те команды Redis, которыми пользуется сервер (значения со сроком, счётчики, хэши, множества,
  списки), поверх таблицы PostgreSQL. Таблицы `inflatia_kv` и `inflatia_research` создаются сами при первом обращении;
  обе ходят через один пул соединений (не больше 3 на функцию).
- `api/_lib/store.js`: если задан `DATABASE_URL` — работает с PostgreSQL ONREZA и к Upstash не обращается. Не задан —
  как раньше, Upstash (так работают превью-сборки).
- `api/_lib/research-store.js`: исследование — в таблице `inflatia_research` той же базы `DATABASE_URL`. Без
  `DATABASE_URL` исследование закрыто (на Upstash оно не открывается).
- `api/_lib/research-link.js` — единственный мост между аккаунтами и исследованием: исследованию — только логин и год
  рождения; аккаунту — удаление участия вместе с аккаунтом и свои записи в «Скачать мои данные».
- `scripts/upstash-to-onreza.mjs` — перенос всех ключей из Upstash со сроками жизни.
- `scripts/db-backup.mjs` — резервная копия обеих таблиц, её проверка, развёртывание в другой базе и сравнение с копией
  Upstash.
- `/api/health` — какая база подключена и отвечает ли (без данных и адресов).
- Проверка — `api/__tests__/pgkv.test.js` на настоящем PostgreSQL: каждая команда отвечает так же, как Upstash; одновременные
  `incr` не теряются; блокировка `set nx` срабатывает один раз; две таблицы не смешиваются; исследование с одновременной
  записью одного аккаунта; копия снимается, разворачивается и сверяется.

## Шаг 1. Аккаунт ONREZA

1. Откройте **app.onreza.ru**, войдите (через GitHub или почту). Создастся личное рабочее пространство (workspace).
2. Подключать репозиторий и создавать проект **не нужно** — сайт на ONREZA не переезжает.

## Шаг 2. Создать базу

1. Раздел **PostgreSQL → Создать базу данных**. Имя — `inflatia`. Для Hobby достаточно имени.
2. Вторая база для исследования **не нужна**: исследование хранится в той же базе, в своей таблице.
3. В настройках базы оставьте **автосон** (auto-suspend) по умолчанию. Учтите: после простоя первый запрос будит базу —
   это лишние секунды на вход или сохранение у первого ученика после паузы. Если это мешает, увеличьте порог автосна.

## Шаг 3. Строка подключения

1. Откройте базу → карточка **Подключение** → режим **Pooled** (через PgBouncer: функции Vercel открывают много коротких
   соединений, пул на стороне сервера для этого и нужен).
2. Нажмите «Показать» и скопируйте строку вида `postgresql://user:password@endpoint.kaiki.onreza.ru:5432/inflatia?sslmode=require`.
   Это секрет: в чат, в код и в GitHub её не вставлять.

## Шаг 4. Перенос данных из Upstash

Делайте в тихое время (ночью): записи, сделанные учениками между переносом и шагом 5, догоняются шагом 6.

1. На своём компьютере (Node.js 22) в папке репозитория: `npm ci`.
2. Значения Upstash — в **Vercel → Storage → база → `.env.local`** (Show secret) или в консоли Upstash (Open in Upstash → REST API).
3. Сначала проверка, ничего не записывая:

   ```bash
   KV_REST_API_URL='…' KV_REST_API_TOKEN='…' node scripts/upstash-to-onreza.mjs --dry-run
   ```

   Скрипт покажет, сколько ключей каждого вида (`string`, `hash`, `set`, `list`).
4. Перенос:

   ```bash
   KV_REST_API_URL='…' KV_REST_API_TOKEN='…' DATABASE_URL='postgresql://…' node scripts/upstash-to-onreza.mjs
   ```

   Числа в конце должны совпасть с проверкой. Повторный запуск безопасен (перезапишет теми же данными).
5. Только если где-то нашлась прежняя отдельная база исследования в Upstash (на 22.11.2026 её нет) — то же с `--research`
   и переменными `RESEARCH_KV_REST_API_URL`, `RESEARCH_KV_REST_API_TOKEN` и той же `DATABASE_URL`: ключи лягут в таблицу
   `inflatia_research`.

## Шаг 5. Переключить Vercel на ONREZA

**Сначала текст для учеников.** Страница «Данные и конфиденциальность» (`src/privacy.jsx`) сейчас говорит, что профиль и
прогресс лежат в Upstash за пределами России. После переключения это станет неправдой. Сам я этот текст не меняю — его
новую редакцию нужно согласовать с юристом и выпустить в тот же день, что и переключение (напишите — внесу согласованный
текст).

1. **Vercel → проект → Settings → Environment Variables → Add**:

   | Переменная | Значение | Окружения | Sensitive |
   |---|---|---|---|
   | `DATABASE_URL` | строка из шага 3 | **Production** | да |

   Для **Preview** (ветки и PR) `DATABASE_URL` не задавайте — превью останется на Upstash и не тронет рабочую базу.
   Если позже захотите отдельную базу для превью — в ONREZA у базы есть ветки (branching): создайте ветку и задайте её
   строку для Preview.
2. **Регион функций.** Функции Vercel сейчас в `iad1` (Вашингтон), база — в Санкт-Петербурге: каждый запрос к базе идёт
   через океан (~120 мс туда и обратно, а вход или сохранение делают несколько запросов). Поставьте функциям ближайший
   к базе регион: **Settings → Functions → Function Region → Stockholm, Sweden (`arn1`)** (или Frankfurt, `fra1`). Делайте это
   вместе с переключением: пока база в Upstash `iad1`, регион `iad1` был правильным.
3. **Deployments → последний Production → ⋯ → Redeploy** — переменные применяются только к новой сборке.

## Шаг 6. Догнать записи и проверить

1. Сразу после того, как новая сборка стала Production, повторите перенос с `--missing` — он перенесёт только ключи,
   которых в PostgreSQL ещё нет (например, ученик зарегистрировался в эти минуты), и не тронет уже свежие:

   ```bash
   KV_REST_API_URL='…' KV_REST_API_TOKEN='…' DATABASE_URL='postgresql://…' node scripts/upstash-to-onreza.mjs --missing
   ```

2. Откройте `https://<сайт>/api/health`. Должно быть:

   ```json
   {"ok":true,"db":"postgres","research":"postgres","region":"arn1"}
   ```

   - `"db":"upstash"` — `DATABASE_URL` не попал в сборку: проверьте окружение Production и сделайте Redeploy.
   - `"ok":false` при `"db":"postgres"` — база не отвечает. Посмотрите **Vercel → Logs** (ошибка `handler error`):
     - `self-signed certificate in certificate chain` или `unable to get local issuer certificate` — сертификат базы подписан
       центром, которого нет в Node.js (например, российским Russian Trusted Root CA). Скачайте корневой сертификат
       (для Минцифры — с gosuslugi.ru/crt, файл в формате PEM), добавьте переменную **`DATABASE_CA`** с его текстом целиком
       (от `-----BEGIN CERTIFICATE-----` до `-----END CERTIFICATE-----`) и сделайте Redeploy. Проверку сертификата не отключайте;
     - `password authentication failed` — строка скопирована не полностью или пароль сброшен в панели ONREZA;
     - `timeout` — база спала дольше обычного; обновите страницу.
   - `"research":"postgres"` — таблица исследования в той же базе. Сбор при этом закрыт, пока протокол — черновик
     (`/api/research?action=status` → `not-started`).
3. Проверьте на сайте: вход в аккаунт, прогресс после перезагрузки, «Сообщить об ошибке» и разбор жалоб у владельца,
   таблица вызова дня.

## Шаг 7. Что делать с Upstash

1. **Не трогайте**, пока не выполнен раздел «Перед удалением Upstash». Если что-то пойдёт не так, достаточно удалить
   `DATABASE_URL` в Vercel и сделать Redeploy: сайт вернётся на Upstash (записи с 20.11 останутся в PostgreSQL — их можно
   перенести обратно тем же способом).
2. Потом данные в Upstash устаревают и только дублируют базу ONREZA. Удалять ли их и когда — решите с юристом
   (`docs/legal-todo.md`): сейчас копия персональных данных лежит в двух местах, одно из них — США. Удаление — в консоли
   Upstash (Data Browser → Flush) или удаление базы в Vercel → Storage. При удалении интеграции Vercel ↔ Upstash база
   удаляется вместе с ней.
3. Переменные `KV_REST_API_URL`, `KV_REST_API_TOKEN`, `KV_REST_API_READ_ONLY_TOKEN`, `KV_URL`, `REDIS_URL` после удаления базы
   уберите из Production и Preview. Превью-сборки тогда будут работать на памяти (без сохранения между запросами) — или
   задайте им ветку базы ONREZA.

### Перед удалением Upstash — по порядку

1. Сменён пароль базы ONREZA (ниже, «Что сделать владельцу сейчас», п. 1) и сайт после этого работает (`/api/health`).
2. Ручная проверка рабочего сайта (там же, п. 4) прошла.
3. Снята копия ONREZA и **проверена развёртыванием** в другой базе (раздел «Резервные копии», пп. 2–3).
4. Снята копия Upstash и сравнена с копией ONREZA (раздел «Резервные копии», п. 4): сравнение пишет «Все долгоживущие
   ключи первой копии есть во второй».
5. Две недели работы без `handler error` в Vercel → Logs.
6. Решение юриста по копии в США.

## Резервные копии

- В ONREZA есть восстановление на момент времени (PITR) — и на Hobby, и на Pro: создаёт новую ветку базы из состояния на
  выбранный момент; окно восстановления видно в настройках базы. Независимая резервная копия хранится отдельно от рабочей
  базы и её веток (docs.onreza.ru → PostgreSQL → «Восстановление и резервные копии»). **Окно восстановления в панели —
  запишите в `docs/data-architecture.md`, раздел 7.**
- Своя копия — `scripts/db-backup.mjs` (нужен только Node.js 22 и `npm ci`; `pg_dump` нужной версии не нужен). Обе таблицы
  — `inflatia_kv` и `inflatia_research`. Строку подставляйте в терминале, не сохраняйте в файлах проекта:

  1. Снять копию:

     ```bash
     DATABASE_URL='postgresql://…строка Pooled из ONREZA…' node scripts/db-backup.mjs
     ```

     Скрипт напишет файл `inflatia-backup-<дата>.jsonl.gz` и числа строк по таблицам — сверьте с числом ключей на сайте
     (на 20.11 было 2545 ключей).
  2. Проверить файл (целостность и хэши): `node scripts/db-backup.mjs --check inflatia-backup-….jsonl.gz`.
  3. **Проверить развёртыванием** — в ветке базы ONREZA (Создать ветку в панели базы → её строка Pooled) или в любом
     другом PostgreSQL, но не в рабочей базе (скрипт откажется, если строки совпадают):

     ```bash
     RESTORE_URL='postgresql://…строка ВЕТКИ…' node scripts/db-backup.mjs --restore inflatia-backup-….jsonl.gz
     ```

     «Развёрнуто и сверено: копия проверена» — это и есть проверенная копия. Ветку после проверки удалите.
  4. Копия Upstash и сравнение (перед удалением Upstash):

     ```bash
     KV_REST_API_URL='…' KV_REST_API_TOKEN='…' node scripts/db-backup.mjs --upstash
     node scripts/db-backup.mjs --compare upstash-backup-….jsonl.gz inflatia-backup-….jsonl.gz
     ```

     Значения не выводятся — только число ключей по префиксам: каких нет в ONREZA и у каких значение другое (у активных
     учеников значения в ONREZA новее — это нормально). Короткоживущие ключи (`session:`, `hit:`, `link:`, `cnt:`) могут
     отличаться.
- Файлы копий — персональные данные: хранить зашифрованными (архив с паролем или зашифрованный диск), не в репозитории
  (`.gitignore` их не пропустит) и не в облаке без шифрования. Копии, снятые во время сбора исследования, удалить в день
  фиксации набора (`research/retention-policy.md`, раздел 4).
- Стандартный `pg_dump` по той же строке тоже подходит (`pg_dump` версии не ниже сервера).
